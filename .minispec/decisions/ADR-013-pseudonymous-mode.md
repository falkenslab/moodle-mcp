# ADR-013: Other people's personal data: minimized, and pseudonymous by default

## Decision

Tools never give other people's contact data (email, phone, address, IP), photos or profile fields, and give activity times only when asked. Beyond that, a pseudonymous mode, on by default (`MOODLE_MCP_PSEUDONYMIZE`, `--pseudonymize` / `--no-pseudonymize`, `configure`), replaces every other person with a stable alias: the client sees `A-7K3F`, never a name, an email or a Moodle user id, and the person using the server resolves aliases on their own machine. Their own name and data stay visible: they are the one using the agent.

- **A library, not a server.** The pseudonym code (`src/pseudonym/`) knows nothing of Moodle and runs inside each server that uses it, exposing nothing to the client: an MCP server for it would hand the agent a `whois`. It becomes a package when a second server needs it, not before.
- **Aliases.** `A-` plus a short base32 HMAC-SHA256 of the person's identifier under a secret key, lengthened on a collision: the same person always gets the same alias, in every course and session, and it can't be undone without the key. The identifier is the best one the service has: an institutional id (Moodle's "ID number" field when set), else the institutional email, else the service's own user id. Cross-service linking is off by default: the service's name enters the HMAC, so two services give different aliases; on, the same person has one alias everywhere their identifier matches.
- **The key.** 32 random bytes in the user's configuration folder, shared by every server on the machine (`%APPDATA%\pseudonym\`, `~/.config/pseudonym/` elsewhere), never inside the browser profile, so deleting the profile to log in again keeps it. Two subkeys derive from it, one for aliases and one for the directory. A marker records that a key existed: if the key is missing then, pseudonymous mode is refused with an explanation instead of a new key silently changing every alias. `pseudonym key export | import | fingerprint` moves it between machines (or shares it in a department) and checks it.
- **The local directory.** Next to the key, encrypted (AES-256-GCM), written under a file lock: per person the alias, the display name, the service ids and HMACs of the email and institutional id (never in clear), first and last seen. A person matched by any identifier keeps their first alias, so an email change doesn't change it; `link` merges two aliases. `pseudonym whois | alias | forget | prune` work offline in the person's terminal; `forget` and `prune` serve erasure and retention.
- **Tools.** Outputs carry aliases instead of names and user ids, and URLs with user ids lose them; write tools take an alias and translate it inside. Free text (submissions, posts) gets known participants' names replaced by their aliases, and contact data detected by patterns (an existing library if `openredaction-spike` finds one good enough in Spanish).
- **Browser fallback tools (ADR-010).** In pseudonymous mode, snapshots get known names replaced and user ids removed from links; screenshots are refused (a picture can't be redacted).
- **Third-party MCP servers** are out of scope: if they need it, an existing pseudonymizing proxy (MCP Conceal, PII Anonymizer) is evaluated before building one.

## Motivation

The server's results go to a language model, often outside the EU. Teachers' tasks need to tell students apart, not to know who they are, and their notes need a stable reference they can resolve later, also across services. Existing tools detect PII in free text and swap it for per-session tokens; none gives a permanent alias from structured data that the agent can't undo, and detection is where they fail (names), while the server knows exactly which fields are people. Encrypting each person's data into the output (a token per student) was considered: legally the same pseudonymization, it sends contact data the model doesn't need, a leaked key would expose everything ever sent, it changes when a name or email does, and it costs hundreds of characters per mention. Off by default would rely on every institution configuring it; on by default is privacy by design (decided by the owner, 9 October 2026).

## Consequences

- Not anonymization: what people write about themselves can still identify them when patterns miss it, and an alias plus enough context can identify someone. Cross-service linking makes that easier, hence off by default. The README says so, lists what each tool sends, and leaves the legal basis, the processing agreement and the international transfer to the institution.
- The alias protects against sending names by accident, not against an agent that reads the key or runs the CLI on the same machine: the README gives the client permissions that deny it.
- Losing the key loses the way back from old aliases, by design; `key export` is the backup.
- Every tool that shows other people goes through one module (`moodle/people.ts`), and tests check that no name, email or user id leaks in pseudonymous mode.
