# ADR-013: Other people's personal data: minimized, and pseudonymous by default

The on/off switch below is replaced by ADR-016's student data policy (`block`, `pseudonymize`, `clear`); the rest stands.

## Decision

Tools never give other people's contact data (email, phone, address, IP), photos or profile fields, and give activity times only when asked. Beyond that, a pseudonymous mode, on by default (`MOODLE_MCP_PSEUDONYMIZE`, `--pseudonymize` / `--no-pseudonymize`), replaces every other person with a stable alias: the client sees `A-7K3F9Q`, never a name, an email or a Moodle user id, and the person using the server resolves aliases on their own machine. Their own name and data stay visible: they are the one using the agent. Only the person turns it off, at start-up in the client's configuration (with a model that runs locally, say); `configure` can turn it on for the session, never off, or the agent could undo it (the same rule as ADR-015's scopes).

- **A sibling library, not a server.** Aliases, the key, the local directory and the CLI live in `@falkenslab/pseudonym` (sibling repository `pseudonym`, its ADR-001 to ADR-003), which runs inside this server and exposes nothing to the client: an MCP server for it would hand the agent a `whois`. moodle-mcp takes it from npm and bundles it.
- **Aliases.** `A-` plus base32 of a keyed HMAC of the person's identifier (pseudonym's ADR-002): the Moodle user id, in the service `moodle@<host>`. The "ID number" field or the email would only matter for linking across services, off by default, and the driver doesn't give them with people, so they're left for when linking is wanted (11 October 2026). The same person always gets the same alias, in every course and session. Cross-service linking is off by default.
- **The key and the directory** are pseudonym's (its ADR-003): one key per user in `%APPDATA%\pseudonym\` or `~/.config/pseudonym/`, shared with other servers and kept out of the browser profile; an encrypted directory with display names and service ids, contact identifiers only as HMACs; a lost key is refused, not regenerated. The person resolves aliases with `pseudonym whois`.
- **Tools.** Outputs carry aliases instead of names and user ids, and URLs with user ids lose them; write tools take an alias and translate it inside (`resolve()`). Text the agent writes to Moodle (feedback, posts) is refused when it holds an alias: people would read it as is, and turning aliases back into names (pseudonym's `reveal()`) isn't exported yet. Names shown without an id (a forum list, a quiz review) become the alias of someone already met, else `[participant]`. Free text (submissions, posts) gets known participants' names replaced by their aliases, and contact data detected by a few checked patterns (emails, Spanish phones, DNI and NIE with check letter, ES IBANs), both through pseudonym's `redact()`: a measured spike found OpenRedaction no better in Spanish and noisy in code (pseudonym's ADR-005, 9 October 2026).
- **Browser fallback tools (ADR-010) and others' files.** Only with names in clear: a page or a file holds names of people not met yet, which redaction can't find, so pseudonymizing them would pretend to protect what it doesn't (11 October 2026; first planned as redacted snapshots and refused screenshots).
- **Third-party MCP servers** are out of scope: if they need it, an existing pseudonymizing proxy (MCP Conceal, PII Anonymizer) is evaluated before building one.

## Motivation

The server's results go to a language model, often outside the EU. Teachers' tasks need to tell students apart, not to know who they are, and their notes need a stable reference they can resolve later, also across services. Existing tools detect PII in free text and swap it for per-session tokens; none gives a permanent alias from structured data that the agent can't undo, and detection is where they fail (names), while the server knows exactly which fields are people. Encrypting each person's data into the output (a token per student) was considered: legally the same pseudonymization, it sends contact data the model doesn't need, a leaked key would expose everything ever sent, it changes when a name or email does, and it costs hundreds of characters per mention. Off by default would rely on every institution configuring it; on by default is privacy by design (decided by the owner, 9 October 2026).

## Consequences

- Not anonymization: what people write about themselves can still identify them when patterns miss it, and an alias plus enough context can identify someone. Cross-service linking makes that easier, hence off by default. The README says so, lists what each tool sends, and leaves the legal basis, the processing agreement and the international transfer to the institution.
- The alias protects against sending names by accident, not against an agent that reads the key or runs the CLI on the same machine: the README gives the client permissions that deny it.
- Losing the key loses the way back from old aliases, by design; `key export` is the backup.
- Every tool that shows other people goes through one module (`src/people.ts`), and tests check that no name, email or user id leaks in pseudonymous mode.
- Scopes (ADR-015) come first: a tool the person left out never reaches the model; pseudonymization applies to the `student-data` tools that are allowed.
- Turning it off for a local model trusts the whole chain to stay local: the client, its logs and telemetry, any transcript sync. Minimization (no contact data, no profile fields) and the scopes apply either way.
