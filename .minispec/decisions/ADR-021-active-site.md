# ADR-021: Several sites, one active

## Decision

The server knows a list of Moodle sites, each with a name, a URL and its own browser profile, and works on one of them at a time, the active site: every existing tool acts on it, unchanged, and `use_site` switches. Sites come from configuration (`MOODLE_MCP_SITES`, `--sites`) and at run time (`add_site`, `remove_site`); run-time sites are saved in the server's data folder and survive a restart. Amends ADR-009: the server now writes one file of its own, the run-time sites.

## Motivation

A teacher with several campuses wants one agent on all of them, and to reuse courses across them (#16). A server per site repeats every tool in the model's context, fixes the list of sites in the client's config, and leaves transfers to the model. A `site` input on every tool (the issue's first proposal) touches all 137 tools and makes the common single-site setup pay for it in every request; an active site changes none of them, and only the transfers, which need two sites, name them (phase 2, after moodle-driver#57). What it gives up, working on two sites in one call, isn't what the use case needs. Decided by the owner, 13 October 2026.

## Consequences

- **Configuration.** `MOODLE_MCP_SITES` (`--sites`) takes two forms. A value starting with `{` is JSON: an object from each site's name to its URL, or to an object with its `url` and, later, options of its own (`{"campus": "https://campus.example.org", "uni": {"url": "https://moodle.uni.es"}}`), so a site can grow settings without a new format. Anything else is a comma-separated list, easy to type in a shell or a client's form, where JSON's quotes need escaping: an item starting with `http://` or `https://` is a URL, the site named after its host (an `=` in its query doesn't matter); any other is `name=url` (`https://campus.example.org`, or `campus=https://campus.example.org,https://moodle.uni.es`). Two sites with the same name, such as two unnamed URLs on one host, stop the server asking to name them. A value that is neither stops the server with a message naming it. Decided by the owner, 13 October 2026. `MOODLE_URL` alone is a one-site list named after its host; with `MOODLE_MCP_SITES` too, it's the first site, ahead of the list, unless the list already has its URL, so a 0.2 configuration that adds sites keeps its active site and profile. Names are short (letters, digits, dots, hyphens), unique; a site without one is named after its host and port (`campus.example.org`, `localhost-8080`); two accounts on one site are two sites, the second named. The first configured site is active at start.
- **Run-time sites.** `add_site({ url, name })` checks the URL as `configure` does (ADR-009) and adds the site, a known URL only under another name (another account); the first site of a server with none takes the profile in use, so a configure-only setup keeps its session; `remove_site` forgets a run-time site and deletes its profile, after confirming with the person; a configured site can only be removed from the configuration. `configure({ moodleUrl })` with no site configured adds a run-time site named after the host and activates it, so today's flow still works.
- **Where things live.** The data folder is `${CLAUDE_PLUGIN_DATA}` when the server runs as a plugin, else `~/.moodle-mcp`. Claude Code gives a plugin's stdio MCP servers that variable: a folder per plugin (`~/.claude/plugins/data/<id>/`), kept across updates and deleted with the plugin by default (its plugins reference, checked on 13 October 2026), so each agent keeps its own sessions and uninstalling removes them. The first configured site keeps today's profile (`MOODLE_MCP_PROFILE_DIR`, or `profile` in the data folder: `~/.moodle-mcp/profile` as now, so no one logs in again); every other site's profile is `sites/<name>/profile` there. Run-time sites are in `sites.json` in the data folder.
- **Switching.** `use_site(name)` closes the active site's browser (its session stays in its profile, ADR-007) and makes the other active; the next tool opens its browser, and `login` its window if it has no session. The active site is kept in memory: a restart starts on the first configured site. `server_info` and the instructions' limits line name the active site and the others; the instructions say to switch with `use_site` and tell the person.
- **Tools.** `list_sites` (read-only: name, URL, active, where it came from; not whether a session is open, which would take a browser per site), `add_site`, `use_site` and `remove_site` are session tools: there under every role, scope and access level, like `configure`. None of them reads or writes Moodle data.
- **Limits and privacy.** The role, access, scopes and student data level are the server's, the same on every site; `configure` narrows them for the session on every site. Aliases already belong to one site (`moodle@<host>` in `src/people.ts`), so nothing about people crosses sites; two accounts on one host share their people's aliases, as they're the same people.
- **Driver.** Each site gets its own browser manager on its profile, created when first used. moodle-driver 0.8 says one profile can hold sessions for several sites, but two accounts on one site can't share one: a profile per site keeps both cases alike, and removing a site removes only its session.
- **Transfers.** One tool, `copy_between_sites`, for activities, sections or a whole course, rather than one per kind (fewer tool definitions): it switches to the source site for a partial or whole backup, anonymous and without people's data, to the target for the restore, deletes the file and puts the active site back, whatever happens.
- **Docs.** Settings, a page on several sites, `server_info`, the tools reference.
